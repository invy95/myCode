# 报名题按用户句式写

用户写「项目背景 / Big Project 四特征」时，用她的清单句式。模型稿如果更顺、更概括，改回她的写法。

## 和模型稿的差别

模型容易做的，不要再做：

- 把第一题的功能列表在第二题开头再讲一遍。
- 把领导写成和投研同事并列的施工角色。领导只作为需求清单的来源。
- 用「三边一起做」「少一边就做不完」「同事打开就能用」收束。
- 把空间收成「一套系统」。她会拆开：业务项目空间、各人 agent 各自学习的日常工作流、单项投研任务单建的项目空间。
- 连锁反应用「提问会对不上」这类结果句。她写操作：资料结构或 API 一变，调用、检索 skills、报告上传都要改；协同空间变了，日报输出地址也要变。

她的句子长这样：

- 先点题，再冒号，功能用顿号和括号举例，不展开定义。例：能协同办公（AI 辅助生成日报等），知识库相关功能。
- 输入写具体材料名。例：领导定的需求清单，同事现有投研手工整理版材料。
- 先写同事提供什么、谁在用，再写「我把这些收成系统」，后面跟做事清单：空间、工作流、API、skills、数据接入、自动推送。
- 缺了谁只用两句：没有同事的资料和口径，投研工作流无法完成。没有我，这些都无法在一个空间内并 AI 化。
- 交付按空间拆开写，并写 API 接到各 agent 后做的三件事：检索、资料整理、上传。

## 改稿顺序

1. 删掉与上一题重复的功能介绍。
2. 领导不进入角色清单，除非用户明确写了领导还做了验收以外的事。
3. 把「一套空间」拆成她区分过的空间。
4. 把抽象连锁改成「哪个接口或地址要跟着改」。
5. 保留她用过的产品名和动作，不换成近义词。

## 同一题里的两段事例各写一件决定

重叠是因为把一次建设拆成两个主题，两段仍按同一条时间线往后写，后一段又带上前一段的解法。

动笔前先写成两件决定，每段只回答这一件的原因、走错的路、处理办法：

分类只分两件，不要再拆细。自定义模型 API 不单列，也不放进选型。

- 决定一：需求理解。先入为主有两处，领导开会也提过：知识库和协同要在同一个空间里，于是要自建；要用最强模型，于是接自定义 API。做的过程中才取舍：自建排期太长，API 不稳定，先跑通稳定更重要。处理是拆开接乐享，Kimi 够用后自定义模型不再立项。
- 决定二：空间用个人工具还是协作工具。路径是 Coze、Work Buddy、再回到 Coze。Work Buddy 个人更好用；领导要手机同步和像企微一样人聊天，所以定回 Coze。

决定一的解法（拆开、乐享 API、检索 skills、停掉自定义模型）不写进决定二。决定二的选型理由不写进决定一。用户改了其中一段，另一段里相同的那一件整句删掉。
